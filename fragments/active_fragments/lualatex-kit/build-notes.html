Build & Release Notes

How the six files are compiled, checked, versioned and filed. The kit page is for readers; this page is for whoever maintains the machinery behind it.

The six .tex files are the deliverable. Everything else is scaffolding: a latexmk configuration, a continuous-integration workflow, a citation file, and a release routine that mints a DOI. This page records why each piece is the way it is, including the parts that failed silently the first time.

02Local build

aPrerequisites
  • TeX Live, installed as described on the kit page.
  • latexmk, included in texlive-latex-recommended on Ubuntu, or available as the latexmk package.
bCompile a single file
latexmk file.tex

No engine flag is needed: .latexmkrc configures LuaLaTeX and Biber. Without that file the equivalent command is:

latexmk -lualatex -pdf file.tex
cCompile all six at once
for f in *.tex; do latexmk "$f"; done
dClean up auxiliary files
latexmk -c    # remove .aux, .log, .toc, .out, .bbl, .run.xml, .synctex.gz
latexmk -C    # the above, and the .pdf as well

03The .latexmkrc file

$pdf_mode   = 4;   # 4 = LuaLaTeX
$bibtex_use = 2;   # use Biber for bibliographies
$clean_ext  = "bbl run.xml synctex.gz";
  • $pdf_mode = 4 selects the engine. Other values: 1 = pdflatex, 2 = ps2pdf, 3 = dvipdf, 5 = xelatex.
  • $bibtex_use = 2 makes latexmk run Biber whenever a bibliography is present, even if the .bib file is not mentioned explicitly.
  • $clean_ext extends the list of files removed by latexmk -c to include Biber's own auxiliaries.
Precedence: the command line beats the config file Running latexmk -pdf file.tex with this configuration lets the -pdf flag override $pdf_mode = 4 and silently falls back to pdflatex. This matters for CI; see section 04.

04Continuous integration

The workflow lives in .github/workflows/build-latex.yml.

aWhat it does

On every push to main that changes a .tex file, the .latexmkrc, or the workflow itself, GitHub:

  1. starts a clean Ubuntu virtual machine;
  2. checks out the repository;
  3. runs latexmk on each of the six .tex files in parallel (a matrix build);
  4. uploads each resulting .pdf as a downloadable artifact;
  5. marks the whole run green or red, depending on whether everything compiled.

Artifacts are kept for 90 days by default. Find them on the repository's Actions tab: open the run and scroll to "Artifacts" at the bottom.

bTrigger paths
paths:
  - '**.tex'
  - '.latexmkrc'
  - '.github/workflows/build-latex.yml'

Edits to the README, the LICENSE or CITATION.cff do not trigger a build, which keeps CI noise low. To force a rebuild, use the Run workflow button on the Actions tab (enabled by workflow_dispatch:).

cThe latexmk_use_lualatex line
- uses: xu-cheng/latex-action@v3
  with:
    root_file: ${{ matrix.name }}.tex
    latexmk_use_lualatex: true

The action's default command line includes -pdf, which, as section 03 explains, overrides $pdf_mode = 4 and brings back pdflatex. Setting latexmk_use_lualatex: true swaps -pdf for -pdflua and keeps the engine as LuaLaTeX. Without this line, CI would build with the wrong engine and say nothing. With it, local and CI builds agree.

dThe matrix
matrix:
  name:
    - modern-lualatex-guide
    - cl-cheatsheet
    - cs-starter
    - romance-comp-ling
    - corpus-stats
    - praat-pipeline

The entries are stems only, with no .tex extension. The input is referenced as ${{ matrix.name }}.tex and the output as ${{ matrix.name }}.pdf. This avoids the foo.tex.pdf artifact-path bug.

fail-fast: false means that if one file fails to compile, the other five keep going, so a single run shows every error and not only the first.

Node.js deprecation warnings are harmless CI runs print "Node.js 20 is deprecated" warnings for actions/checkout@v4 and actions/upload-artifact@v4. GitHub is moving its runners from Node 20 to Node 24, and the action maintainers will update upstream. Nothing needs fixing here.

05CITATION.cff and release metadata

A machine-readable citation file in format v1.2.0. GitHub builds a "Cite this repository" button in the sidebar from it, and Zenodo reads it when it mints a DOI on release.

aWhat to update per release

Two fields, and nothing else:

version: 2.1.0
date-released: "2026-11-01"
bWhy there is no email address

CITATION.cff is public, and leaving the email out prevents scraping. The ORCID iD plus the name is enough for attribution; anyone who needs to reach the author can use the repository's issue tracker.

06Release workflow (GitHub → Zenodo)

aOne-time setup (done for this repo)
  • Log in to Zenodo with GitHub OAuth.
  • Switch on this repository in Zenodo's list of GitHub repositories.
  • That creates a webhook which fires on every GitHub release.
bPer release
  1. Bump the version in CITATION.cff (version: and date-released:).
  2. Commit everything that belongs in the release: 
    git add -A
git commit -m "vX.Y.Z: <short summary>"
git push
  3. Wait for CI to go green on that push. If it is red, fix it before tagging.
  4. On GitHub, open Releases → Draft a new release.
  5. Tag: vX.Y.Z, with "Create new tag on publish".
  6. Title: vX.Y.Z — <one-line summary>.
  7. Description: a dedication paragraph if there is one, then a change list organised by intent (pedagogical, infrastructure, portfolio), not by file.
  8. Leave "Set as the latest release" checked.
  9. Publish the release.
  10. Within about two minutes Zenodo receives the webhook, downloads the tag snapshot, mints a new DOI and sends an email.
  11. Verify the Zenodo record: author name, ORCID link, and an abstract that matches CITATION.cff. If anything is off, edit the record on Zenodo directly. The DOI is permanent, but the metadata can be edited.
cVersioning policy
  • Patch (X.Y.z): typo fixes and minor polish, no new content.
  • Minor (X.y.0): new sections or files, non-breaking additions.
  • Major (x.0.0): removed files, breaking changes, significant restructuring.
dConcept DOI and version DOI
  • The concept DOI always resolves to the latest version. Cite it when you mean the kit in general.
  • Each release also gets its own version DOI. Cite it when you need one specific version, for reproducibility.

Both appear on the Zenodo record page.

07Deploying this page

The kit page lives in the portfolio repository under fragments/active_fragments/lualatex-kit/ and is published through GitHub Pages. This notes page sits in the same folder.

aThe PDF folder

The compiled PDFs sit in pdf/ next to the HTML. They are updated by hand, either from local compiles or by downloading the CI artifacts and committing them.

bUpdating the pages

Each page is self-contained: CSS inline, no build step. Edit, commit and push to the portfolio repository, and GitHub Pages redeploys within a few minutes.

If the download links break again Download links must point at the raw file, in the form github.com/<user>/<repo>/raw/main/<file> (or the equivalent on raw.githubusercontent.com), and never at /blob/main/, which returns a GitHub web page instead of the file. Watch out for code assistants in the editor: they do not know which format is needed and may silently rewrite the URL into the broken form.

08Known issues and future work

Praat spectrogram is a placeholder praat-pipeline.tex currently uses a gray placeholder image. Replace it with a Praat-exported PDF once one exists. The TikZ tier coordinates assume a 4.5-unit-wide timeline, so adjust them after the replacement.
Bibliography style cs-starter.tex has biblatex commented out. If you uncomment it, use style=unified (the LSA Unified Stylesheet, from the biblatex-unified package, part of texlive-full). Do not use biblatex-sbl: that is the Society of Biblical Literature style, not linguistics.
tipauni, not tipa The kit standardises on tipauni, which is Unicode-native and works with fontspec and polyglossia. The old tipa package is incompatible with modern Unicode fonts and should not be loaded.
gb4e needs \noautomath Always load \noautomath immediately after \usepackage{gb4e}. Omitting it causes a parameter-stack crash on any subscript or superscript. Every template in the repository already does this.

09Troubleshooting

01CI fails with "File 'xyz.sty' not found"

The CI's TeX Live is comprehensive but not exhaustive. Add a step before the compile step to install the missing package:

- name: Install missing packages
  run: sudo tlmgr install xyz
02CI fails but the local build works

The likely cause is a .latexmkrc disagreement (section 04) or TeX Live version drift. Compare the output of lualatex --version locally with the version printed in the CI log.

03The Zenodo record has the wrong author

Edit the record on Zenodo directly: open it and choose "Edit". Metadata changes do not need a new DOI. CITATION.cff is only read at release time, so to fix it for the next release, edit CITATION.cff and update the current Zenodo record by hand.

04The font cache is stale after installing a font
  • Linux: fc-cache -fv
  • macOS: luaotfload-tool --update (no sudo)
  • Windows: usually automatic
05GitHub lists one person as two contributors

It is not two accounts; it is two different user.email values on different machines. Set the same values everywhere:

git config --global user.email "you@example.org"
git config --global user.name  "Your Name"

Then make sure the same address is added to the GitHub account and marked as primary. New commits will be unified. Old commits can be rewritten with git filter-repo, but that is rarely worth the trouble.
