Azure vs. Open Source: Four Pipelines, One Verdict

Two ETL projects, each built twice — once on Microsoft Azure, as the hands-on vehicle for DP-900 exam prep, and once entirely open-source and local, purely to see what the difference would actually be. It held up both times.

Background

Where this started

The brief was DP-900 (Azure Data Fundamentals) exam prep, and the vehicle was Bee Haven — a beekeeping-data medallion pipeline (bronze → silver → gold) on Azure Data Lake Storage Gen2, processing hive sensor readings enriched with weather data via Azure Data Factory and Synapse Spark. As an open-source believer, I also built the same architecture on SeaweedFS — a local, Apache-2.0, S3-compatible object store — originally just to compare tooling, before it grew into a genuine parallel implementation worth documenting on its own.

After Bee Haven, I wanted a second, deliberately small project with real live data, to test something specific: would a genuinely simple automation be simple in Azure? A German electricity-price monitor (fetch a free API daily, clean, store, visualize) seemed like the right size to find out — and, again, got built as a pair: once on Azure, once as a local Docker Compose stack.

What follows is the honest record of both pairs — where each one actually finished, not where it was originally planned to.

Across All Four

The Pattern

The same handful of issues, twice, on two unrelated projects.

🔑

Identity confusion, every time

Bee Haven needed three separate managed identities each granted their own storage role. The electricity Function App hit the same lesson in a new context: the auto-granted role is almost never for the storage account you actually care about.

⏰

The undocumented trigger bug, twice

The same silent, non-firing ADF schedule trigger — correctly configured, confirmed "Started," never observed to actually fire — independently on two unrelated projects. A well-documented, long-standing community issue, not a config mistake.

🧭

Wizard defaults built for someone else

Flex Consumption silently blocked on trial subscriptions. A user-assigned identity created by default when nothing asked for one. A resource provider that needs manual, one-time registration before anything works.

🐛

Open source's real advantage isn't "no bugs"

SeaweedFS lost a whole bucket once too (no volume mount on the first container). The local electricity build had three genuine logic bugs of its own. The difference was minutes to diagnose and fix, not days.

🧩

Fewer moving parts, fewer failure classes

No cross-service managed-identity handshake, no black-box trigger, no separate compute tier to provision for a 17-row job — just a script talking directly to storage. Most Azure roadblocks above simply have no equivalent locally, because the layer that could fail isn't there.

Not a Clean Sweep

Being honest about how this actually finished

Two wins, two honest shortfalls — not four identical outcomes

Neither open-source build finished exactly as ambitiously planned, and neither Azure build finished with a perfectly clean scorecard either. The electricity project's local build stayed flat: SeaweedFS sits in the Docker Compose file unused, storage went to the plain filesystem instead — no real S3-API parity attempt like Bee Haven's SW build has. The electricity project's Azure build, meanwhile, never got its dashboard: Power BI Desktop is Windows-only, this was all built on a Mac, and after two working core pipelines in one week, that felt like the right place to stop rather than force it. Bee Haven's Azure trigger has the same shape of gap — built correctly, never confirmed firing. This page states all of that plainly rather than smoothing it into a tidier story than what actually happened.

Status

Where things stand

  • Bee Haven SeaweedFS — genuine parallel build, S3 API + WebDAV, 2 real bugs fixed
  • Electricity Azure — ingestion, cleaning, and dedupe logic all individually proven correct
  • Electricity Local — working dashboard with heatmap + time series, 3 real bugs fixed

🔜 Known gaps, left open on purpose

  • Both Azure schedule triggers: correctly configured, never confirmed firing live (known platform bug)
  • Electricity Local: no real SeaweedFS/S3 parity attempt yet
  • Electricity Azure: dashboard skipped, Mac/Power BI mismatch
  • DP-900 gaps: security beyond RBAC, relational/NoSQL services, broader cloud concepts
