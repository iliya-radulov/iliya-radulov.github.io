Roadmap Stage 2: Mobility, SmolVLA & Voice Polishing

The three threads that outgrew the original Voice + Vision + Arm roadmap, now tracked on their own — the original goal is closed and achieved.

Stage 1 set out to combine a Voice Kit, Vision Kit, and one stationary arm into a single voice-triggered system — done, as of the first voice-triggered autonomous rollout. Everything below grew out of that project but is a genuinely larger scope: a mobile robot, a language-conditioned policy, and an unrelated voice-quality side project. Tracked here so the closed roadmap can stay a clean historical record.

Thread 1 — LeKiwi Mobility ◉ In Progress

A wheeled base — genuinely new hardware direction, not an extension of the stationary arm. Inspired by ALOHA-2; settled on LeKiwi as the affordable entry point, with a documented upgrade path to XLeRobot later.

Where it stands

  • ✅ Base kit delivered, both arms assembled and validated on the Mac (MPS), all 9 motor IDs set
  • ✅ Pi 5 power question resolved — Yahboom Power Expansion Board ordered, ETA 8–15 Sept
  • ⚠️ Three defects found on delivery, formal complaint filed with Seeed (Order #13152): wrong buck converter, arm mount doesn't fit the base plate, undersized screws. Full details: LeKiwi Base: Delivery, Defects & Wheel Motor Setup.
  • ☐ Physical daisy-chain assembly currently blocked on the arm-mount defect — waiting on Seeed's replacement parts
  • ☐ ACT validation pass on the LeKiwi arm once physically assembled (hardware/pipeline check, not a SmolVLA data run)
  • ✅ Camera/mount upgrade complete (see Thread 2) — new wide-angle cameras and standardized mounts now installed across the setup, and the calibration convention (parallel-to-table, true-center) is fixed the same way on every arm, which should help once cross-hardware transfer to LeKiwi is retested
⸻ ⬇ ⸻

Thread 2 — Voice-Conditioned Control via SmolVLA ◉ In Progress

Swap the ACT policy for SmolVLA, a true Vision-Language-Action model with an actual language encoder — genuine free-form voice-conditioned behavior, not just fixed trigger phrases.

Where it stands

  • ✅ Compute blocker resolved — new ML Desktop built and confirmed (Ubuntu 26.04, RTX 5060 Ti 16GB, CUDA 13.2 verified). Full spec and reasoning: Hardware Notes.
  • ✅ Base network trigger protocol (Flask + Vosk + Piper) already proven in Stage 1 — reusable as-is for SmolVLA's command path
  • ✅ New wide-angle cameras installed (110° vs. the previous 75° FOV) — fixes the known camera-coverage failure (position P7) and gives a consistent setup going into multi-task recording
  • ✅ SO-101 rig migrated from Mac to a Pi 5 — root-cause fix for recurring camera-crash-during-rollout errors (the Mac's lack of native USB-A was forcing cameras and the arm controller to share hub bandwidth). Full diagnosis and debugging arc: SO-101 Rig Migration: Mac → Pi 5.
  • ✅ Record → transfer → train pipeline proven end to end on the new hardware — first Pi-5-hosted dataset (28 episodes) recorded, transferred to the ML Desktop, GPU confirmed genuinely functional. Full setup, storage policy, and open questions: ML Desktop: LeRobot Setup & First Pi 5 Dataset.
  • ☐ Immediate next step: run ACT training on the validation dataset to confirm the full pipeline, before moving to genuine SmolVLA multi-task data planning
  • ☐ The real next step after that: design and record a genuinely multi-task dataset. Current data is single-task throughout (pick-and-place only) — language conditioning is meaningless without task variety to actually condition on. Deliberately deferred to its own planning session, not decided in passing.
  • ☐ Validate whether the Pi 5 (4GB) can run SmolVLA inference at usable speed at all, or whether a Mac/desktop-tethered setup is needed long-term
  • ☐ Once trained: re-test the original text-triggered backdoor attack from the poisoning investigation — SmolVLA is the architecture it was actually designed for, unlike the earlier mismatched ACT test
⸻ ⬇ ⸻

Thread 3 — Voice Polishing: Dimitar (Piper) & XTTS Experiments ◉ Parked, ready to resume

Fixing pronunciation/stress issues in the bg/dimitar Piper voice used by the assistant. A genuine side branch — never blocked Stage 1, and doesn't block Stage 2 either.

Where it stands

  • ✅ Round 1 (94 clips, RunPod): voice character present, artificial pacing. Full write-up: round 1 report.
  • ✅ Round 2 (138 clips, continuous-passage recording): closer match to the real voice, real improvement. Full write-up: round 2 report.
  • ✅ Full runbook documented for both rounds — round 3 can start quickly whenever picked back up
  • ⏳ Round 3 now genuinely easier than before — the new ML Desktop means local training, no more RunPod GPU-rental dance
  • ☐ Swap the polished round-2 voice into the live assistant on voice — currently still running the original unmodified Dimitar; zero technical risk, just hasn't been done yet
  • ☐ XTTS fine-tuning experiment on the same dataset — planned purely as a curiosity project, not part of core assistant work
  • ✅ Zero-shot XTTS voice cloning (Bulgarian reference → Russian output) already tried, purely for fun
