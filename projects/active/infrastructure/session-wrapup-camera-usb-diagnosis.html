New Camera Integration: USB Enumeration Crash — Diagnosis & Fix

First lerobot-rollout after installing the new Innomaker cameras crashed within ~1 second, every run. Full elimination sequence, root cause, and fix.

Current state: crash diagnosed and resolved — root cause was a marginal USB port position in a two-hub daisy chain, not the cameras, lerobot, or MPS. Fix applied by swapping physical ports; rollout now runs to completion.

Also decided: arm control/inference is moving to the Pi (native USB ports, headless) to remove this class of problem going forward. A fresh training dataset recorded on the new cameras is next, since the existing checkpoint's poor performance here is expected domain shift, not a new bug.

Symptom

After installing two new cameras (Innomaker U20CAM-1080p-S1 as main, U20CAM-720P as gripper) on the SO-101 rig, running the existing so101_bgdiv_v1 checkpoint via lerobot-rollout crashed consistently, always within about a second of the control loop starting:

TimeoutError: OpenCVCamera(0) latest frame is too old: 503–526 ms (max allowed: 500 ms).

Always OpenCVCamera(0). Never the other camera. Every single attempt.

Root Cause

Not either camera, not lerobot, not MPS, not connection order. The actual cause was a marginal USB port position somewhere in the physical chain: Mac (no native USB-A) → TP-Link UH700 powered USB 3.0 hub → second hub, with both cameras and the arm's serial connection sharing this chain. Two hubs in series adds real USB-tree depth, which matters more for high-bandwidth video devices than for the arm's low-bandwidth serial link — and the new cameras' higher native resolution (1280×720 / 1920×1080, vs. whatever the originals negotiated) pushes more data through that same marginal chain than before.

lerobot's camera wrapper deliberately uses a minimal internal buffer (always read the freshest frame, not a queued one) — correct behavior for real-time control, but it means there's no slack to absorb even a brief enumeration hiccup. A standalone script using OpenCV's default buffering quietly tolerates the exact same instability that crashes the real control loop.

Fix Applied

Swapped which physical port each camera plugs into on the hub chain. Crash resolved; rollout runs to completion without camera errors.

Separate, Expected Issue: Pick-and-Place Quality

With the crash fixed, the so101_bgdiv_v1 checkpoint's actual pick-and-place performance on the new cameras is poor. This is not a new bug — it's expected domain shift. The checkpoint was trained entirely on the old cameras' resolution, FOV, and color/sensitivity response; the new cameras are a genuinely different visual input distribution. This is exactly the scenario the roadmap's open item ("reference photos before the camera swap, validate after") was anticipating. The real fix is a fresh training pass recorded on the new camera feed — already the plan, not a new problem to chase.

Decision: Move Inference to the Pi

Going forward, arm control and rollout will run through the Pi (4 or 5) rather than the Mac. Reasoning: the Pi has 4 native USB ports and can run headless — removing the two-hub daisy-chain entirely, along with the class of enumeration-instability problem it caused here. This isn't just a workaround for today's issue; it's a more robust topology for the arm+camera setup generally, independent of which specific hub or port was marginal this time.
