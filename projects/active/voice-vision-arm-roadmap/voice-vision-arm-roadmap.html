Project Roadmap: Voice + Vision + Robot Arm

A staged plan for combining a Google AIY Voice Kit, AIY Vision Kit, and a WitMotion SO-ARM101 leader/follower arm pair into one integrated system — built on Raspberry Pi and Hugging Face's LeRobot framework.

Status update, August 2026: Phases 1–3 remain complete and stable. Recent work has focused heavily on two side branches — a data-poisoning/security investigation (see Phase 3) and early planning/procurement for Phase 7 (mobility). Phase 4 (Vision) and Phase 5 (Voice) have not been actively worked on recently and remain the next priority for the core voice+vision+arm integration goal once the current dataset-rebalancing and mobility-procurement work settles.

  • ✅ Voice Kit assembled, WiFi fixed, Google Cloud speech recognition working — see the final report and setup guide
  • ✅ Vision Kit assembled, WiFi fixed (own hostname aiy-vision), camera hardware replaced after original sensor failed, face detection + joy scoring + object detection all confirmed working on-device — see the final report, initial troubleshooting log, and camera fix summary

  • ✅ Calibrate servos, run standard so101_follower setup
  • ✅ Basic teleoperation: move leader, watch follower mirror it live — see the full setup log (60Hz, stable, arm + camera together)

Phase 3 — Record Demonstrations ✅ COMPLETE

  • ✅ Use LeRobot's recording tools to capture leader→follower sessions for a simple task — see the first Pi 4 attempt and the Mac migration & 30-episode dataset
  • ✅ Produces a first dataset — useful on its own, even before any training
  • ✅ Beyond the original plan: a full ACT policy was trained on the recorded data, and the follower arm achieved fully autonomous pick-and-place — see the complete project write-up
  • ✅ Security/robustness side investigation: reproduced and corrected a data-poisoning backdoor attack methodology from published research. Discovered mid-investigation that the ACT architecture has no language-conditioning pathway (a text-prompt trigger cannot function on it), then designed and validated a genuine, working visual trigger backdoor instead. Two full write-ups: the corrected text-trigger investigation and the working visual-trigger report
  • ✅ Dataset generalization work: discovered a severe position bias after extending the original single-position dataset (36 vs. ~6 episodes per position) caused a trained model to consistently drift back toward the over-represented position even when correctly locating the object elsewhere. Rebuilt with a fully balanced, position/orientation-varied dataset (5 positions × 3 orientations × repeats, 120 episodes total, ~24 per position, original single-position episodes deliberately excluded) — testing of the rebalanced model in progress

Phase 6 Extension — Voice-Conditioned Control via SmolVLA (planned, not started)

A natural convergence point for Phases 4, 5, and 6: rather than voice commands only selecting between pre-trained ACT checkpoints (ACT has no language input — confirmed via source-code inspection during the poisoning investigation), swap the policy architecture to SmolVLA, a true Vision-Language-Action model with an actual language encoder. This would allow genuine free-form voice-conditioned behavior, not just fixed trigger phrases.

Planned architecture

  • Brain Pi (Pi 5): Pi AI Cam attached, running vision + arm control
  • Voice2 Pi (second Pi 4, reusing Phase 1's working AIY Voice Kit software): listens for commands, sends them over the network to the Brain Pi
  • Training/inference compute: given SmolVLA's heavier backbone, initial training stays on the Mac (MPS); the Pi 5 (4GB) likely cannot run SmolVLA inference at usable speed unaccelerated — to be validated empirically before assuming otherwise
Bonus: this also finally enables properly re-testing the original text-triggered backdoor attack from the poisoning investigation, on the architecture it was actually designed for (SmolVLA), rather than the mismatched ACT test that produced this project's earlier corrected/negative result.

Open items

  • ☐ Validate whether Pi 5 (4GB) can run SmolVLA inference at usable speed at all, before assuming a Mac-tethered setup is required long-term
  • ☐ Will need genuinely multi-task demonstration data (multiple distinct task prompts) to make language conditioning meaningful — current dataset uses a single fixed task string throughout
  • ☐ Design the simple network trigger/command protocol between Voice2 Pi and Brain Pi
Milestone note: Phases 2–3 (arm teleoperation + recording) are a complete, showable project on their own — no need to wait for Voice/Vision integration to call that a finished build.

Hardware notes

On the Pi 4 (1GB) — is it enough?

For teleoperation and inference, yes. For recording, no — this was tested and corrected mid-project. Don't worry about not getting the 2GB model — even 2GB wouldn't be enough to train imitation-learning/VLA policies at reasonable speed; that kind of training really wants a machine with a GPU. The practical split, confirmed by actual testing rather than assumed upfront:

  • Pi 4 (1GB) is fine for: running the Voice/Vision Kit software, driving the arm via LeRobot's control/teleoperation scripts, and running already-trained lightweight policies for inference.
  • Recording demonstration datasets should not happen on the Pi 4 (1GB): testing showed lerobot-record hit a real ~4-6Hz ceiling against a 30Hz target when running arm control, camera capture, and real-time video encoding together — a genuine hardware limit, not a tuning problem. See the Mac migration log for the full diagnosis.
  • Training (Phase 6) should happen elsewhere: a laptop with a decent GPU, or a rented cloud GPU session. Record data off the Pi (a Mac with MPS acceleration proved effective), transfer the dataset if needed, train off-device, then deploy the resulting model back to the Pi for inference.

This is standard practice in the LeRobot ecosystem — the low-power board is the "body" running the final model, not the machine collecting data or doing the heavy training. The 1GB Pi 4 remains a fine choice for its actual role; recording and training were always going to need more capable hardware.

On the PCIe M.2 HAT (Pi 5) — SSD vs. AI accelerator, researched and decided

Investigated whether an M.2 AI accelerator (e.g. Hailo-8L) could enable on-device SmolVLA inference on the Pi 5, as an alternative to the Mac-tethered setup in the SmolVLA extension plan above.

Finding: Hailo's toolchain (Dataflow Compiler, Model Zoo) is built and proven for CNN-based vision models (YOLO, classification, segmentation). Community reports (e.g. attempts to deploy DINOv2/v3, a Vision Transformer) describe the compiler lacking support for certain transformer-internal layers. No evidence found of a successful VLA model deployment on Hailo hardware. SmolVLA's transformer/attention-based architecture falls much closer to the "documented trouble" category (ViT-like) than to Hailo's proven CNN use case.

Decision: skip the AI accelerator for this purpose — the engineering risk (undocumented, likely-unsupported operators) isn't worth it for this project's scale. Use the M.2 slot for an NVMe SSD instead — safe, immediately useful for dataset/model storage and swap headroom on the Pi 5's 4GB RAM, no research risk. Revisit the accelerator question only if Hailo's transformer support meaningfully matures, or for a separate, genuinely CNN-shaped task (e.g. real object detection for Phase 4).

On the 10" touchscreen (currently idle on the Pi 3)

Worth keeping in reserve — good candidate uses once further along:

  • A live dashboard Pi (showing Vision Kit's camera feed + detections during arm demos)
  • A simple GUI for triggering pre-recorded voice/arm actions without needing to actually speak, useful for debugging

Not needed for Phases 1–3, but there's no reason to buy a second display when this one's sitting idle — repurpose it once Phase 4 or 5 is reached.
