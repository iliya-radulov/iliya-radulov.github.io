Hardware Notes

Compute and platform decisions for the Voice + Vision + Robot Arm project, with the reasoning kept alongside each one

On the Pi 4 (1GB) — is it enough?

For teleoperation and inference, yes. For recording, no — this was tested and corrected mid-project. Don't worry about not getting the 2GB model — even 2GB wouldn't be enough to train imitation-learning/VLA policies at reasonable speed; that kind of training really wants a machine with a GPU. The practical split, confirmed by actual testing rather than assumed upfront:

  • Pi 4 (1GB) is fine for: running the Voice/Vision Kit software, driving the arm via LeRobot's control/teleoperation scripts, and running already-trained lightweight policies for inference.
  • Recording demonstration datasets should not happen on the Pi 4 (1GB): testing showed lerobot-record hit a real ~4-6Hz ceiling against a 30Hz target when running arm control, camera capture, and real-time video encoding together — a genuine hardware limit, not a tuning problem. See the Mac migration log for the full diagnosis.
  • Training (Phase 6) should happen elsewhere: a laptop with a decent GPU, or a rented cloud GPU session. Record data off the Pi (a Mac with MPS acceleration proved effective), transfer the dataset if needed, train off-device, then deploy the resulting model back to the Pi for inference.

This is standard practice in the LeRobot ecosystem — the low-power board is the "body" running the final model, not the machine collecting data or doing the heavy training. The 1GB Pi 4 remains a fine choice for its actual role; recording and training were always going to need more capable hardware.

On the PCIe M.2 HAT (Pi 5) — SSD vs. AI accelerator, researched and decided

Investigated whether an M.2 AI accelerator (e.g. Hailo-8L) could enable on-device SmolVLA inference on the Pi 5, as an alternative to the Mac-tethered setup in the SmolVLA extension plan.

Finding: Hailo's toolchain (Dataflow Compiler, Model Zoo) is built and proven for CNN-based vision models (YOLO, classification, segmentation). Community reports (e.g. attempts to deploy DINOv2/v3, a Vision Transformer) describe the compiler lacking support for certain transformer-internal layers. No evidence found of a successful VLA model deployment on Hailo hardware. SmolVLA's transformer/attention-based architecture falls much closer to the "documented trouble" category (ViT-like) than to Hailo's proven CNN use case.

Decision: skip the AI accelerator for this purpose — the engineering risk (undocumented, likely-unsupported operators) isn't worth it for this project's scale. Use the M.2 slot for an NVMe SSD instead — safe, immediately useful for dataset/model storage and swap headroom on the Pi 5's 4GB RAM, no research risk. Revisit the accelerator question only if Hailo's transformer support meaningfully matures, or for a separate, genuinely CNN-shaped task (e.g. real object detection for Phase 4).

Reasoning behind the config:

  • VRAM range established empirically first, not guessed: ran test workloads on RunPod against rented A4000 and RTX 3090 instances to find the actual working range for this task, before pricing any hardware. Settled on a 16–24 GB VRAM window as the requirement.
  • GPU sourcing: first choice was a used RTX 3090 (sits in the target VRAM range) — but used units were running ~€2500, out of budget. Pivoted to a new system with a reasonable total price under €2000, landing on the RTX 5060 Ti 16GB as the in-budget option that still clears the empirically-set VRAM floor.
  • Local box vs. cloud split, decided deliberately, not a fallback: this machine is for local testing/iteration; heavier training runs stay on rented cloud compute (RunPod) as needed.
  • CPU and RAM sequencing: GPU was fixed first as the binding constraint, then CPU (Ryzen 9 9900X) and RAM (32GB/6000MHz) upgraded as reasonable-cost additions within remaining budget.
  • Storage split, deliberate: the 1TB M.2 NVMe is for everyday/active-project use only. An old HDD will be added for local bulk storage, with archival data ultimately living on the home server.
  • OS: Linux, matching the native OS already used for the robotics stack.

Pi 5 Power Board — buck converter comparison and decision

The LeKiwi base kit's onboard buck converter turned out to be a GYEC-DC0503 (12V→5V, 3A) — usable for light loads, but under the Pi 5's recommended 5V/5A supply. Rather than accept the shortfall, three replacement options were compared:

  • Generic AliExpress 5V/5A PD module — rejected. Its DC barrel-jack input path is rated only 7–12V. The LeKiwi battery is nominally 12V but its actual charge-limit voltage is 12.6V (confirmed from the battery's own label: 3S Li-ion, 11.1V nominal / 12.6V charge limit) — meaning a freshly-charged battery would exceed this module's input ceiling right when it's used most. The module is really designed around USB-PD wall-charger input, not a raw battery feed.
  • Treedix UPS HAT — rejected. Explicitly listed for Raspberry Pi Zero/2B/3B/3B+/4B only, not Pi 5 — a different power-negotiation architecture, not just an older/cheaper option.
  • Yahboom Raspberry Pi 5 Power Expansion Board — selected. 6–24V input (comfortable margin over the battery's 12.6V full-charge voltage), 5V/5A output via the Pi 5's actual PD protocol (not a generic step-down pretending to be compatible), input options including a DC5.5×2.1 barrel jack matching the battery's existing cable exactly (no adapter needed). Purpose-built for Pi 5 mobile-robot use cases specifically.

Ordered from the Yahboom Official Store on AliExpress for €18 (vs. €32 for the identical board on Amazon.de), same 8–15 Sept delivery estimate either vendor. Two other listings were checked and passed over along the way: the same Yahboom board sold direct via a second AliExpress listing (redundant once the Official Store price was known), and a T-plug/Deans-connector cable variant (rejected once the battery's actual connector was confirmed to be a standard DC barrel jack, not a T-plug — no adapter needed either way).

Physical fit note: the Yahboom board's mounting posts are designed to stack directly onto the Pi 5, but the Pi 5 in this build already lives in a metal case — the two won't stack together as shipped. Planned workaround for now: wire the board in with a short USB-C cable rather than physically stacking it, keeping the metal case intact. A custom laser-cut or 3D-printed mounting plate remains a possible later upgrade once there's bandwidth for it, but isn't blocking assembly.
