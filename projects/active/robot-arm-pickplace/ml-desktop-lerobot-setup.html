Storage policy, decided today

  • Datasets (raw episodes/video): cache locally at ~/.cache/huggingface/lerobot/local/ during active training, then archive to the home server (storage1/training/lerobot/, same convention as the existing bgdiv archive) once a training run is complete. Not kept long-term on the ML Desktop's NVMe.
  • Checkpoints: live in the project folder on disk (so101-pickplace-project/lerobot/outputs/train/<run_name>/checkpoints/) — not git-committed (binary weights bloat git history badly). Archived to the server once superseded, same as datasets.
  • Git repo holds only genuinely small artifacts: reports, scripts, roadmap docs, session notes, config.

First real Pi-5-hosted dataset

so101_pi5_act_validation — 28 episodes, 16,758 frames. Schema: 7 positions × 4 orientations × 1 repetition, deliberately no repeats — this run is pipeline validation, not intended as a robust trained checkpoint. Single-shot coverage trades trajectory-averaging robustness for full spatial breadth.

lerobot-record \
    --robot.type=so101_follower \
    --robot.port=/dev/ttyUSB1 \
    --robot.id=my_follower_arm \
    --robot.cameras='{"main": {"type": "opencv", "index_or_path": "/dev/video2", "width": 640, "height": 480, "fps": 30}, "gripper": {"type": "opencv", "index_or_path": "/dev/video0", "width": 320, "height": 240, "fps": 30}}' \
    --teleop.type=so101_leader \
    --teleop.port=/dev/ttyUSB0 \
    --teleop.id=my_leader_arm \
    --dataset.repo_id=local/so101_pi5_act_validation \
    --dataset.single_task="Pick up the object and place it in the target" \
    --dataset.num_episodes=28 \
    --dataset.episode_time_s=20 \
    --dataset.reset_time_s=8 \
    --dataset.push_to_hub=false

Note: no fourcc: MJPG in this config — the Innomaker cameras reject MJPG negotiation via OpenCV entirely (set_ok=False, confirmed earlier on the Mac). Running raw format instead; this is fine on the Pi since each camera now has its own dedicated USB 3.0 port, with no bandwidth contention to work around.

A real gotcha: the folder name isn't what you think

lerobot-record appends a timestamp suffix to the actual folder name, even though a clean repo_id was passed in. The real path was so101_pi5_act_validation_20260905_160525, not the bare so101_pi5_act_validation used in the argument. This caused an initial LeRobotDataset lookup failure — it tried the literal repo_id, didn't find a local match, then incorrectly attempted to resolve it against the Hugging Face Hub, producing a 401 error. Lesson: check the actual terminal output from lerobot-record for the real save path immediately after recording, rather than assuming the bare repo_id is the folder name.

Locations:

  • ML Desktop: same path under ~/.cache/huggingface/lerobot/local/, transferred via scp, verified byte-identical via matching episode/frame counts on both ends (28 / 16,758)

Open questions — carried forward, still genuinely unresolved

What should SmolVLA training data actually look like?

Unlike ACT (which benefits from dense position/orientation grids since it learns the task from scratch), SmolVLA starts from a pretrained VLA base with broad visual/language priors. Fine-tuning data needs likely shift toward:

  • Genuine task/language variety — not just repeating "pick and place" at different coordinates, but distinct instructions like "push the object left" or "stack X on Y," each with its own demonstration episodes
  • Less emphasis on exhaustive spatial grid coverage per task, more emphasis on representative variation (positions, backgrounds, lighting) within each task

Not yet decided: the concrete episode schema (how many tasks, how many episodes per task, position/orientation coverage per task) — deliberately deferred to a dedicated planning session rather than decided in passing.

Does a checkpoint trained on SO-101 transfer to LeKiwi / XLeRobot?

Empirically partially tested, not fully resolved:

  • An earlier LeKiwi cross-hardware test (the bgdiv_v1 checkpoint, newspaper background) produced 0% success — but diagnosed as a calibration-mapping mismatch (correct approach direction, consistent positional/angular offset) rather than a vision or policy-generalization failure. Camera mount imprecision was also a contributing factor at the time.
  • Mitigations now in place that should improve a future retest: camera mounts standardized (identical official design across all arms), cameras now identical hardware across arms, calibration reference convention now deliberately fixed (parallel-to-table true-center calibration).
  • XLeRobot (bimanual) is a harder case — its action/state space is roughly double a single-arm policy's, so a single-arm SO-101 checkpoint's action head won't transfer directly. The frozen vision encoder portion of a VLA model might transfer even when the action head doesn't — a real, common pattern in VLA fine-tuning, not yet tested for this specific case.
  • Next real test: once LeKiwi is fully assembled (pending: replacement 3D-printed arm mount + correctly-sized screws from the Seeed complaint, Pi 5 power board arriving 8–15 Sept), retest cross-hardware transfer with the now-standardized camera/calibration setup and see whether the earlier offset problem persists or resolves.
