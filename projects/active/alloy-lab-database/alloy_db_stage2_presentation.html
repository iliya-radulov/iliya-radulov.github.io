Stage 2 transforms the lab‑book foundation of Stage 1 into a validated research platform. Every instrument pipeline is built on real data. Every number in the database has a known provenance. The schema is designed for machine learning — and the infrastructure is now ready for Stage 3.

"The hard, instrument‑specific work is done. What remains is science."
— Stage 2 completion summary, September 2026

Why this exists

Experimental materials research generates a lot of files — XRD patterns, VSM hysteresis loops, SEM images, synthesis notes — spread across instrument computers, personal laptops, and shared folders. The analysis lives in Origin projects. The samples are tracked in spreadsheets. The connection between "what we made" and "what we measured" is mostly in someone's head.

Stage 1 built the data‑capture layer: a composition calculator, literature cross‑checking against three external databases, and basic file import. Stage 2 adds the analytical layer: real, validated characterisation pipelines for every instrument in the lab, with results stored in a structured schema designed — from the start — for machine learning.

Three pipelines, built from scratch

Each pipeline was built on real lab data, validated against a known reference, and integrated end‑to‑end before the next was started. No shared code, no shared assumptions — each instrument has its own failure modes.

XRD

X-ray diffraction — peak fitting pipeline

Validated against NIST SRM 660c (LaB₆) certified reference material — lattice parameter converging to within 0.0001 Å of the certified value.

  • Background subtraction and Kα2 stripping (Cu anode)
  • Neighbour‑aware peak fitting — each peak fit uses local context, not isolated windows
  • R² quality score per peak — low‑quality fits flagged, not silently averaged
  • Scherrer crystallite size and d‑spacing extracted automatically
  • Results stored in two tables: long‑format xrd_peaks (one row per peak) and wide‑format xrd_features (ML‑ready, one row per sample)

VSM

Vibrating sample magnetometry — multi‑segment pipeline

End‑to‑end tested against real production database — three real bugs found and fixed during integration, including a NaN-masking issue that silently hid a 60 K temperature jump.

  • Instrument auto‑detection: PPMS VSM / MPMS3 / ACMS — each has different column conventions
  • Mass extraction from file header (primary) or filename (fallback, with confidence flag)
  • Automatic segmentation: MH loops / MT scans / idle / corrupted — rolling‑window classification, not naive point‑to‑point derivatives
  • Second‑quadrant Hc/Mr extraction — crossing‑point interpolation on the descending branch only
  • Temperature coefficients α(Hc) and β(Mr) fitted when multiple loops at different temperatures are present
  • Isothermal entropy change ΔSm via Maxwell relation — with a check that distinguishes genuine isothermal sweeps from full bipolar loops before attempting the calculation
  • Demagnetising correction and BHmax for cuboid samples

SEM

Scanning electron microscopy — unified metadata + phase fraction

Built and tested against real images from three instrument manufacturers. Two real physical findings emerged during development — one corrected a material identity assumption (NdFeB vs MnGa), one confirmed that automated thresholding was correctly detecting real magnetic domain contrast, not a segmentation artifact.

  • Three manufacturers, three completely different metadata conventions — unified into one schema automatically
  • Zeiss: proprietary compressed binary TIFF tags (already solved in Stage 1, extended here)
  • JEOL: sidecar .txt file, custom $KEY value format — scale bar in pixels + real units for exact pixel calibration
  • Tescan: sidecar .hdr file, standard INI format — PixelSizeX directly in metres, 16‑bit image data
  • Phase fraction via Otsu thresholding — offered as a starting suggestion, not forced: operator adjusts the threshold live and saves the confirmed result
Design decision — why operator judgment is required

Simple global thresholding worked well on one real JEOL image (correctly traced the grain‑boundary phase) and failed in two different ways on others — texture confusion on a Tescan image (which turned out to be real magnetic domain contrast, confirmed via Kerr microscopy), and noise confusion on a Zeiss image. A pipeline that pretends to automate a judgment it cannot reliably make is worse than one that is honest about its limits.

Schema — designed for machine learning from the start

The Stage 2 schema additions are not just storage — they are a feature matrix. Every table was designed with the eventual ML query in mind: what goes in the X matrix, what goes in the y vector.

Interactive tools — operator in the loop

Three standalone tools, each launched from the Data Viewer with the current file pre‑loaded and auto‑analysed. The operator reviews the result, adjusts parameters if needed, and saves confirmed results directly to the database. No manual transcription. No copy‑paste errors.

Tool · XRD

XRD Analyzer

Live prominence/distance controls, per-peak accept/reject, mean R² recomputed from accepted peaks only. Save to DB replaces previous analysis for that sample.

Tool · VSM

VSM MH Analyzer

Full file loaded, auto-segmented. Adjustable branch-detection sensitivity per segment. Accept/reject per segment. Save to DB updates Hc/Mr for confirmed segments.

Tool · SEM

Phase Fraction

Otsu threshold as starting suggestion. Live slider, optional invert. Calibrated area readout in µm². Save stores the operator-confirmed fraction — not the Otsu guess.

What the building actually taught

🧲
Instrument metadata is not automatically trustworthy

Zeiss stores metadata in proprietary compressed binary TIFF tags — not in any standard field. JEOL stores it in a sidecar text file using its own key format. Tescan uses INI format and stores pixel size in metres directly, making it the easiest of the three. Three manufacturers, three completely different conventions — none of them documented in any accessible specification.

🔬
A "segmentation failure" turned out to be correct physics

Otsu thresholding failed on a Tescan image — apparently detecting directional surface texture rather than compositional phases. A Kerr microscopy image of the same sample region confirmed the "texture" was real magnetic domain contrast. The algorithm was correct; the physical interpretation needed updating. The material was also misidentified (NdFeB assumed, MnGa actual) — both mistakes were caught before anything was committed.

⚗️
The synthesis screener now records its own reasoning

When the screener flags a composition as physically blocked (e.g. phosphorus vapour loss during iron melting), it now saves the full reasoning — not just the flag — into the synthesis table. Someone picking up the sample months later will know exactly why arc melting was ruled out and what alternatives were suggested, without needing to re-run the screener or find the original notes.

⚡
Atomic percent is now computed automatically

Every new sample entry computes and stores both weight percent and atomic percent — immediately, from the calculator's output, using IUPAC atomic weights. Previously this was a manual backfill script run occasionally. The compositions table now has a composition_type column distinguishing aimed, measured, and reference compositions.

🛠️
path_repair.py — because files move

After a folder rename broke every file path in the database, a repair tool was built that scans all stored paths, identifies broken ones, searches for missing files by filename under a given root, handles ambiguous matches interactively, and updates the database with confirmed new paths. Running it confirmed one broken path; the file was found in three copies on two different drives.

Infrastructure — three machines, one database

On 3 September 2026, the database was migrated from a local Docker container on the development laptop to a dedicated home server. The migration took one session with zero data loss.
